Themis AI Runtime — Demo Architecture and Use Cases

Themis at the core, the AI harness as bounded execution infrastructure. Prepared 2026-09-26 from the locked decision records (openspec/changes/themis-v0 D-T-1..8, l5-witness-events D-W-1..6, themis-integration D-I-1..9). Status: architecture locked; implementation milestones I-M0..I-M5 pending.

The claim the demo defends. Themis remains the authority for security truth while the harness remains bounded execution infrastructure. A real Finding in Themis is remediated by governed AI execution; the execution is verified and independently reconstructed; a human proposes and a different human decides; the model never touches the decision and the harness never writes security truth.

1. System context

Themis is the system of record: six bounded-context services over PostgreSQL, deployed on the enterprise VM. The harness is the eleven-layer governed execution chain with one deployment anchor. They meet at exactly two doors: a read door (the harness reads a projected Finding over HTTP) and a decision door (a Themis-owned CLI reads the harness record locally and raises a Proposal to Governance).

Figure 1. System context on the enterprise VM: Themis at the core, the harness beside it, humans on the outside, two doors between them.

2. Harness architecture and where Themis plugs in

Every layer already exists and is operationally proven under anchors rsys@3..@5. The integration adds no layer: it fills the seams the harness left for Themis and adds L5-owned witnesses to the record so that production can be replayed by the layer that executed it.

Figure 2. Harness layers L1–L11 with the G1 anchor; the read door leaves through L4, the decision door enters the record plane from Themis's side only.

2.1 Locked boundaries that shape the diagram

  • Read door (D-I-3). ThemisSeam.Read is an HTTP client. get_finding serves id, release, faultline, CVE, stage, components; positions and proposals are stripped. The anchor pins themis_contract (endpoints, two OpenAPI spec hashes, Themis commit), never live data. The read-scope key lives only in the harness environment.
  • Decision door (D-I-1, D-I-5, D-I-6). cmd/themis-intake is Themis-owned, runs on the same host, takes the execution tuple only, resolves it through D-T-1..6, and raises a Governance Proposal as an authenticated human. acceptProposal by a separate authenticated key creates the Position.
  • Witnesses (D-W-2, D-W-3, D-W-6). L5 writes one l5-transition per state-machine edge and one l5-op per subprocess and per egress through a writer-fixed handle; the sink enforces a closed class→writer table, folded into the constitution hash (D-W-4).
  • Walls (D-I-7). Exactly one Themis package imports four read-only harness packages; the harness imports no Themis code; neither side can execute or write through the other.

7. Deployment topology for the demo

Figure 6. One VM, two checkouts, one anchor (rsys@6), three keys. The contract pins the interface; the data is live.

7.1 Host-act order (D-I-8)

  1. Themis side: auth required on Governance and Registry; three keys issued with authadmin; deployed commit checked against contract.json; demo Finding established through the pipeline (fixture feed if OSV is unreachable).
  2. Harness side: W-M1..W-M3 and the module rename landed and proven hermetically; rsys@6 minted on the host from the host's tree; opened and validated; rsys@5 withdrawn; demo execution.
  3. Decision side: operator raises through themis-intake; decider accepts; no dev: witness.

8. Deliberately out of scope

  • Vulnerability-feed ingestion beyond the one demo advisory; Knowledge Builder; CVE enrichment.
  • Themis's Intelligence Gateway (AI proposals) — off for the demo so the only proposal is the human's.
  • Automated acceptance; any Position created by the harness or the model.
  • Multi-skill pipelines; harness-to-Themis traffic other than the single read door.
  • Process authentication and key custody beyond Themis's authentication administration.
