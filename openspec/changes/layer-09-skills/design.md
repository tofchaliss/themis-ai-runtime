# Design: Layer 9 — Skills & Procedures

Grill OPEN 2026-09-07. §2 collects folded decisions as questions close; §3 is the question list.

## 0. Position in the flow

L9 sits *before* submission: it is authoring-and-instantiation machinery. The L7 loop stays the sole executor; L9 produces what the loop consumes. Everything a skill "does" at runtime must already be expressible as the seven governed envelope references — if it isn't, that is a gap in a lower layer, not a license for L9 side channels.

## 1. Hard invariants (inherited, not grillable)

- Model output advisory; deterministic controls enforce (Day-0).
- A skill may instantiate/narrow governed ceilings, never define them (cross-layer principle: L2 Plan⊆Contract · L4 Grant⊆Ceiling⊆Registry · L5 Spec⊆Ceiling · L7 workflow⊆ceiling⊆registry).
- Skills are procedures, never authoritative business truth (ADR-009).
- External content is data; instruction identity and authority are L1-owned; untrusted content reaches the model fenced through L2.
- Governed artifacts: versioned, DisallowUnknownFields, trailing-content refusal, SHA-256 into the record, fail-closed loaders.
- Nothing is defaulted; every absence is a typed, named refusal.
- Approval vocabulary stays reserved fail-closed (Q-L7-9) until its own grill.
- A recorded deterministic state transition identifies the exact governing rule, the selected branch, and the actual causal event — the verifier never guesses (owner principle, L7 final acceptance 2026-09-08).

## 2. Locked decisions (fold target)

### D-L9-0 — Runtime position: L9 never executes at runtime (LOCKED 2026-09-08)
L9 is a pre-submission plane: define → resolve → validate → instantiate. Instantiation produces an ordinary governed envelope; L7 alone executes the resulting walk. There is no L9 runtime walker to constrain — second-orchestrator prevention by reachability, not discipline. The older architecture wording "L9 executes procedure" is superseded: execution responsibility was absorbed into shipped L7.

### D-L9-17 — Proof gate: five registers, investigate-cve@1 slice, unmodified production loop (LOCKED 2026-09-08, Q-L9-17)
P0 slice: investigate-cve@1 — exercises the distinctive L9 path (composition, instantiation, seam, attribution, replay) on v1 capabilities only (read_file/write_file/declare_done; no run_command, no approval); remediate-dependency deferred until OPEN-2 provides meaningful deterministic verification. Five registers per §4. The live proof runs through the UNMODIFIED production L7 loop — a special L9 test executor would weaken the proof. **Owner's closing attack, adopted (Register C primary, live in E):** alter only the Skill provenance of a successfully instantiated envelope to claim a different registered Skill whose executable composition differs, submit directly to L7 — L7 must either preserve the claim as opaque attribution while executing the actual envelope, or reject the inconsistency deterministically if the envelope contract requires internally consistent attribution; it must NEVER resolve the claimed Skill or silently adopt its workflow (origin says S@99 ≠ L7 executes S@99). Acceptance: three-state verdicts per milestone, independently challenged; Class-3 security/test/architecture reviews; archive preserves traceability Q-L9 decision → design mechanism → register → test → live evidence → review disposition.

### D-L9-16 — Revision and the ratchet: two gates, informed governance, no auto-promotion (LOCKED 2026-09-08, Q-L9-16)
Skill revision occurs only through the existing registration door (append-only, new version). **Two gates, never collapsed:** registration review = safety/architectural conformance — precedes ANY execution including ratchet evaluation (no evaluation backdoor; unregistered candidates cannot be evaluated by running); ratchet evaluation = quality — ordinary governed tasks under the registered candidate (ordinary SubmitTask/L7/L4/L5/L6; no evaluation execution mode, no special authority in either direction), producing evidence for governance. Registration establishes executability, never production endorsement or superiority; production reliance/non-reliance/withdrawal are governance/deployment decisions. **No auto-promotion:** no harness code path may register, promote, withdraw, or select a Skill version from evaluation results — no "if score < X: withdraw_skill()"; the ratchet informs, humans promote (L11 human-only-promotion pattern preserved); a poor score is evidence supporting withdrawal, never a trigger. **No reduced review:** identical registration gate for every authorship source; AI provenance may raise reviewer attention, never lower the bar (Q-L9-7 applied). **No proposal artifact type in v1** (no SkillProposal/status/lifecycle machinery; existing artifact/evidence mechanisms suffice; formal proposal lifecycle is the future L11 grill's question). **Evaluation attribution:** the evaluation-vs-operational distinction should be recordable but is task/deployment attribution, never Skill identity or execution semantics — use existing Class-4 context; if no suitable purpose dimension exists, record it as an L11/L6 attribution gap rather than adding an L9 field. Evaluation and operational walks use identical authority and machinery; physical workspace/state placement stays deployment policy (same governance/record plane ≠ mandated same physical topology).

### D-L9-15 — Approval: unrepresentable in v1, enforced by unreachability (LOCKED 2026-09-08, Q-L9-15)
v1 Skills contain no approval declarations or mechanism — no approval field in the manifest (a field would tempt a second approval semantics inside L9); approval-vocabulary workflows are already unloadable (Q-L7-9 reserved fail-closed), so in-walk approval requirements are unrepresentable, not refused late. Approval-worthy effects (commit, push, Themis mutation, release approval) are outside the v1 execution ceiling — no capability, no credential, no ingress — so "approval required before commit" is enforced as "the harness stops before commit": prevention by unreachability, stronger than simulated approval. Skills whose method includes such effects terminate at the governed egress hand-off. **Owner wording:** in v1, governed human review of the egress hand-off is the external governance boundary at which approval, where required, may occur; the harness has no approval channel and cannot treat that review as an in-walk event (egress review is not automatically approval; L9 infers nothing from it). **Future channel (deferred, pre-committed):** approval enters as governed workflow condition/events in L7's vocabulary, reviewed within the composition — never an L9 mechanism; approval discharges a condition and never grants authorization (post-approval acts still need their own L4 authorization + L5 constraints — "human approved" ≠ "model may do anything"); approver authentication/permission/scope/expiry/replay/model-observability questions belong to that future control-plane grill; L9 merely consumes the resulting vocabulary. **P0 check:** all six P0 Skills (investigate-cve, analyze-sbom, remediate-dependency, investigate-build-failure, security-code-review, release-security-review) are meaningfully expressible without in-walk approval — no v1 architecture gap.

### D-L9-14 — Verification: skill-required structure, capability-executed, L10-evaluated, governance-decided (LOCKED 2026-09-08, Q-L9-14)
Verification is expressed by Skills only as workflow structure: a verification phase with typed gate outcomes and required transition conditions — never skill-carried executable logic, custom verdict algorithms, or model instructions constituting a verification mechanism. Any deterministic verification computation is a registered L4 capability executed under L5 (future run_build/run_tests/run_scan class, OPEN-2-gated); L9 may structurally require it but cannot authorize, execute, or classify its output. **Ownership chain (no layer does another's job):** Skill requires → L7 enforces gate structure → L4 authorizes → L5 executes → L2 classifies/transports → L10 evaluates verification semantics → Governance decides security meaning/acceptance. No circularity: the Skill only says "this workflow requires the gate outcome PASS"; what PASS establishes is outside L9. **Authority (the D-L9-9 deferred decision):** classification belongs to the producing capability under L2's existing taxonomy; a capability may be REGISTERED derived-eligible (registration property, like all source classification), but an individual result classifies derived only when registered computation + deterministic execution + governed environment + complete computational provenance (capability identity/version, computation/config identity, execution context, input/output hashes, task identity) are actually satisfied — eligibility is capacity, not promotion. Model-relayed verification claims ("I ran the tests; PASS") remain external-untrusted regardless of Skill context; a Skill can never say "this output is derived", promote model content, or define authority classes. **v1 honesty:** no qualifying deterministic verification capability exists (run_command is OPEN-2); v1 Skills impose verification structurally with advisory evidence via read capabilities; no v1 verification output receives derived authority. COMPLETED remains a structural claim about the walk and its required gate outcomes.

### D-L9-13 — The envelope is the seam; L7 stays skill-blind; provenance is preserved, never interpreted (LOCKED 2026-09-08, Q-L9-12)
L9 interacts with L7 only by producing an ordinary governed task envelope + its effective referenced artifacts, submitted through the existing Open · SubmitTask · ReadStatus seam. No new L7 primitive (no SubmitSkillTask/InstantiateSkill/ExecuteSkill; instantiate→submit convenience is caller-side composition, not an orchestration primitive). **Zero trust discount:** L7 must remain correct even if the L9 validator is completely buggy — L9 validation is early admission hygiene; L7 validation is authoritative enforcement (clean fault-containment boundary). **Provenance:** Skill provenance travels with the instantiated envelope and is preserved into the task record, but L7 MUST NOT interpret it for authorization, workflow selection, transition, capability, context, or security-truth semantics — the invariant is locked first; the exact schema representation (an additive, explicitly non-semantic attribution field, envelope version bump) is an implementation amendment (Class 2/3), not an L7 architectural reopening. L7 never resolves/looks up/validates/derives anything from Skill identity. **Attribution consistency, stated epistemically:** the record can deterministically DETECT an inconsistency between declared Skill composition and the independently recorded effective artifact identities (catalog pins vs recorded hashes) — detection of inconsistency, not attribution of forgery intent. **Optionality qualified:** hand-assembled envelopes need no Skill attribution; a Skill-instantiated envelope MUST carry it — enforced by the L9 production contract, not by L7 (L7 never determines which case it is). **Carried proof requirement:** a Skill-attributed envelope and an equivalent hand-assembled envelope with identical executable fields must produce identical L7 control behavior — the operational proof that provenance is metadata, not hidden workflow authority; plus negative proof that altering/removing/misrepresenting provenance cannot change the walk.

### D-L9-12 — No Skill references: recursion unrepresentable; sequencing external; lineage ≠ authority (LOCKED 2026-09-08, Q-L9-11)
Skills cannot call, include, or reference other Skills in v1. The manifest contains no Skill-reference field, making recursion, nesting, and cycles structurally unrepresentable (no cycle/depth machinery to secure). Runtime Skill-to-Skill invocation stays prohibited (D-L9-8) and belongs to the future L8 delegation question. Reuse ≠ reference: two Skills pinning the same immutable artifact hashes (valid, independently reviewable) vs a Skill referencing a Skill (invalid — dependency semantics L9 would then govern: transitive review collapse, recursive identity, withdrawal propagation, workflow splicing). External sequencing permitted: an authorized caller may chain independently governed tasks; one task's output enters another only as Class-3 input through L2 classification/fencing — no authority inheritance, no trust transfer ("A completed" makes B neither more trusted nor authorized). **Lineage is not authority:** the record may carry input-origin lineage (T2.input.origin = T1.output) but T2 independently satisfies every submission/resolution/capability/execution/governance rule. **Residual (recorded, ownership L8-vs-L9 deliberately OPEN):** a governed multi-Skill pipeline — the sequence itself a reviewed executable object (sequence semantics, aggregate authority/budgets, failure propagation, cancellation, approval boundaries, atomicity, whether the sequence requires review) — is deferred to a dedicated grill and must never be implemented through Skill references or nesting (no skill_ref field, ever, under pipeline pressure).

### D-L9-11 — Running tasks are immutable w.r.t. their Skill; mid-walk mismatch is invariant failure (LOCKED 2026-09-08, Q-L9-10)
A running task is immutable with respect to its Skill definition. At instantiation the exact Skill identity and every pinned artifact are resolved ONCE (normative invariant, not implementation advice), bytes verified against pins BEFORE the task becomes executable, and the resulting execution representation is fixed for the task lifetime — the running walk has no catalog or artifact re-resolution path (no arrow back to the catalog during the walk; procedure text included — it is resolved/verified/assembled once, never a per-phase file read creating a hidden mutable-storage dependency). New versions and withdrawal therefore have no effect on a running task; a crash cannot resume against a different Skill (non-terminal closed at startup; retry is a new explicit instantiation against the then-current catalog — S@3-before-crash + S@4-after-crash continuation is unproducible). **Attribution honesty:** recorded hashes must correspond to the bytes actually admitted into the execution representation (catalog pin = resolved-bytes hash = assembled identity), closing the substitution gap between catalog resolution and execution; composition hash stays top-level identity, artifact hashes reconstruction evidence. **Mid-walk re-read mismatch = invariant failure** (freeze → seal → FAILED, never a recoverable error): the decisive criterion is loss of attribution integrity — the system can no longer prove the task executes the reviewed composition it claims — not mere file mutation; routing it through tool-error would imply a normal recovery path exists. **Withdrawal is not runtime revocation in v1:** running tasks continue, exposure bounded by governed execution limits (wall-clock floor); "withdraw and terminate running instances" is runtime cancellation — authority propagation + lifecycle + deployment semantics — a separate future control-plane grill.

### D-L9-10 — Versioning: immutable name@version→hash bindings, append-only catalog, exact pins (LOCKED 2026-09-08, Q-L9-9)
Skill identity is an exact name@version binding to an immutable composition hash; the hash is authoritative, the handle human-facing. Registration requires manifest/catalog agreement (two-way; mismatch refuses); an existing name@version can never be rebound (S@3→H2 refused permanently; new hash = new version). Catalog append-only: no deletion, no replacement; states active|withdrawn only. Withdrawal: remains in catalog, remains addressable for historical interpretation, refuses new instantiation (typed, deterministic), never mutates historical task records — no COMPLETED_BUT_WITHDRAWN, no retroactive re-evaluation, and **no withdrawal event in any task execution record** (catalog governance history records it; execution truth and governance interpretation stay separate: L6 says what happened, governance says what it means now). Pinning absolute: exact name@version only — name-only, @latest, and ranges refused ("latest" is a mutable lookup policy, not a version). Task attribution records name@version + composition hash + all pinned artifact hashes — sufficient immutable identities to reconstruct exactly which reviewed composition was instantiated, defending against catalog drift. Retry: every task independently instantiated against an exact version; retry_of is task lineage only, zero version inheritance (T1→S@3, T2→S@4 legitimate and truthfully recorded). **Withdrawal race (TOCTOU):** resolution and instantiation observe one atomic catalog state — resolve exact version → verify ACTIVE → obtain immutable composition identity → instantiate; a Skill instantiated before withdrawal remains valid for that task (identity already pinned); withdrawal affects future instantiation only.

### D-L9-9 — Skill output: zero added authority, governed provenance only (LOCKED 2026-09-08, Q-L9-8)
Skill execution adds no authority to any output; each output retains the authority its producing layer already assigns — model content advisory/external-untrusted; egress artifacts hand-offs awaiting governed review; the L6 record operational truth (record truth ≠ security truth); the terminal a structural fact that the governed workflow reached it. COMPLETED proves workflow termination under an identified method with its typed verification outcomes; it never proves correctness, remediation, safety, or acceptance — those remain Themis governance decisions (durable(local)/transferred/accepted stay distinct). Skill identity contributes governed provenance which may increase evidentiary weight WITHOUT changing authority class (same class + stronger provenance + typed procedural evidence = greater weight; never external-untrusted→governed promotion). **No authority delegation to outputs:** procedure text can never make "because this Skill completed, accept X" effective — acceptance sits outside L9/L7; an egress report's Skill/Status/Verification fields are provenance and structured evidence, never an Enterprise Position. **Single identity chain:** skill identity travels via the existing attribution/composition-hash mechanism (task → skill_composition_hash → workflow_hash → terminal); no second Skill identity channel in the terminal vocabulary (no COMPLETED_UNDER_SKILL_X — that duplicates identity and creates reconciliation problems). The authority classification of verification outcomes is deliberately OPEN — decided solely in Q-L9-14, not leaked here.

### D-L9-8 — The model may author, never admit; instantiation is external to the walk (LOCKED 2026-09-08, Q-L9-7)
The model may author Skill- or Procedure-shaped artifacts, but authorship confers no authority. Skill-shaped is a data property, not an authority property: unregistered artifacts are external-untrusted data, structurally unexecutable. Executable Skill identity exists only through Themis-governed catalog registration of a reviewed composition hash. Four structural walls: (1) no catalog-writing capability exists in any registry (pinnable by decoded registry scan, the L6 no-state-verb precedent); (2) catalog storage is disjoint from every task-writable root; (3) Skill resolution is catalog-only — L9 never scans for skill-shaped artifacts; (4) identity is the registered composition hash — content resemblance cannot establish identity ("bytes look like the reviewed Skill" is explicitly rejected). A proposed Skill is data: governance may retain it as evidence, egress it, review, reject, modify, or discard it — consumption as review input never constitutes admission. **Instantiation-trigger boundary (locked here, not deferred to L8):** in v1 Skill instantiation is external to the walk — no model output, procedure text, L7 transition, or L4 capability can directly or indirectly invoke instantiation or submit a task; instantiation occurs only through the governed task-submission boundary. Future model-driven delegation (parent/child tasks, authority derivation, budget division, recursion, cancellation, child-result classification) is an explicit L8 architecture + security grill — not implicit in Skill semantics. Ratchet boundary: AI experience → proposed artifact → governance validation → human/governed promotion → registered revision → future deterministic execution; the AI can suggest how Themis improves itself but cannot make the suggestion become Themis behavior.

### D-L9-7 — The instantiation surface: closed four-class field taxonomy (LOCKED 2026-09-08, Q-L9-7′ — instantiation question taken early; draft Q-L9-13 absorbed here)
The instantiation surface is a closed, enumerated field list. **Class 1 — skill-fixed (immutable):** workflow, workflow ceiling, context contract, procedure artifact/reference, grant structure, input schema. **Class 2 — caller-narrowable:** tool quotas and task wall-clock deadline only; effective_value ≤ skill_bound; integer/bounded-value substitution only; the deadline is an execution bound, never a workflow parameter (max_model_turns stays fixed — a different turn budget is a different reviewed revision). **Class 3 — task-state:** task_id, retry_of, target repo + pinned SHA, typed schema-validated inputs → the payload; selects WHAT the method operates on, never HOW; remains external-untrusted even though required for instantiation; reaches the model only through the established L2 classification/framing boundary — supplying input to a Skill never makes it an instruction. No skill-level repository allow-patterns in v1: subject applicability is an authorization/policy question (governance), and skill-metadata authorization would create a second authorization surface beside L4. **Class 4 — deployment-governed (outside the instantiation surface):** registry, model binding, provider execution limits, state/artifact roots, deployment config; recorded as task attribution; never Skill authority and never caller-instantiable infrastructure. **Skills are model-agnostic in v1:** no requires_model, no model-property vocabulary; a future required-model-properties compatibility predicate (deployment-checked, never selection authority) is a separate deferred architecture question. Instantiation produces the ordinary governed envelope + effective grant + effective spec (template hash AND effective hash recorded, extending the L7 grant_envelope/grant_effective pattern) under a closed placeholder vocabulary (@workspace, @task_id, @input.<field> into declared-substitutable spec/payload fields only — never procedure text, workflow, contract, ceiling). **Closed-world rule (owner wording):** Class-1 pins immutable; Class-2 narrows explicitly bounded execution quantities only; Class-3 selects subject, stays external-untrusted; Class-4 is deployment-governed, not Skill authority; no instantiable field may alter executable semantics; any field not explicitly enumerated as instantiable is refused.

### D-L9-6 — The workflow (and its ceiling) are frozen at review; one Skill = one workflow (LOCKED 2026-09-08, Q-L9-6)
A Skill selects exactly one reviewed workflow by immutable pin. The workflow is not an instantiable field — not modified, parameterized, replaced, or extended at or after instantiation; it reaches L7 byte-identical to the reviewed pin, and the composition hash + L7's recorded workflow hash jointly prove reviewed lattice = executed lattice. L7 remains sole owner of workflow execution/transition semantics; a Skill cannot alter δ, add control vocabulary, modify constitution floors, or introduce workflow variants. max_model_turns stays inside the pinned workflow — "same Skill, fewer turns" is a separately reviewed revision. **Workflow ceiling frozen in v1:** instantiation cannot replace, raise, or tighten it; deployment/runtime policy may constrain whether a Skill may be instantiated/executed, but such constraints are never represented as a modified Skill ceiling. Rationale (owner): capability narrowing is safely monotonic because it removes authority; workflow-ceiling narrowing can alter executability and therefore reviewed behavior — the ⊆ principle does not auto-generalize from grants to ceilings. **One-Skill-one-workflow:** no selectable variants, no caller-selected workflow paths — that would make L9 a conditional composition/planning surface and break the atomic review unit. Carried forward to the instantiation-surface question: the closed field list must distinguish ordinary task inputs from anything capable of changing executable semantics.

### D-L9-5 — Skills narrow tool reachability; quotas are caller-narrowable upper bounds (LOCKED 2026-09-08, Q-L9-5)
A Skill never selects or authorizes tools. Two influence mechanisms only: structural narrowing (grant template + per-phase capability sets, ⊆-checked against ceilings and registry, subtractive only — reachability can be removed, never created) and advisory procedure text (zero authority). Runtime selection stays model-proposed and L4-gated per call. Requiring ≠ invoking: a Skill may require work structurally (phases whose exits fire only on typed gate outcomes); invocation authority exists nowhere in a Skill; nothing in L9/L7 auto-invokes. **Quotas:** the Skill's grant-template quotas are upper bounds; instantiation may narrow, never raise (effective_quota ≤ skill_quota ≤ workflow_ceiling), still checked through the existing L7/L4 chain. This is a controlled substitution surface under the D-L9-4 discipline: the quota field is explicitly declared instantiable, downward integer substitution only — no expressions, no conditional quotas, no procedure-text substitution, no capability addition, no authorization.

### D-L9-4 — Zero new interpreters; no executable logic anywhere in a Skill (LOCKED 2026-09-08, Q-L9-4)
A Skill contains no new executable logic or interpreter. Its workflow is declarative control data executed by the already-proven L7 δ; every other artifact is declarative data for already-proven interpreters (loaders, L2 composer, mechanical schema validator, closed-vocabulary placeholder substitution). Instantiation yields an envelope and nothing else; any computation a method needs is a registered L4 capability executing in L5 during the L7 walk. Introducing any new interpreter into L9 is an architecture change requiring its own grill. **Input-schema v1 cap (locked here):** closed vocabulary — type (string|integer|boolean), required, max_length (bounded), enum (bounded literals); explicitly excluded: regex/pattern, $ref/recursion, conditionals, expressions, computed defaults, coercions, custom validators, scripts, arbitrary JSON-Schema dialect features, callbacks. The validator performs only bounded structural checks. **Procedure-text boundary:** caller input is NEVER substituted into procedure text — the procedure artifact is byte-immutable from review to delivery (L1 instruction handling); caller inputs travel only via L2/context or governed payload, external-untrusted, fenced. The model may correlate the two; L9 never turns untrusted caller data into instruction material. Net: no L9 runtime + no L9 interpreter + no procedure templating + no schema programming + no executable verification scripts.

### D-L9-3 — Ownership: author ≠ governance ≠ machinery (LOCKED 2026-09-08, Q-L9-3)
Three axes, never blended: authorship (any permitted source — confers no trust or authority), catalog/registration/review (Themis governance — registering the reviewed composition hash is the owning act), machinery (harness — load/validate/resolve/instantiate, mechanical enforcement only, never content). An unregistered skill-shaped artifact is data and structurally unexecutable — presence is not authority (the repository-instructions trust model). **v1 prohibition:** repository-sourced or externally sourced Skills cannot become executable through discovery; they require a future explicit activation architecture + review gate (a Skill carries workflow + grant potential — more authority than repository prose). Steward ≠ authority: catalog metadata for accountability/review routing only; execution authority comes from the registered composition. **Review evidence v1:** registration in the governed catalog IS the evidence; the entry binds the exact composition hash + governance metadata; an asserted reviewed=true or author metadata is never evidence. No signature machinery in v1 — signatures solve actor attestation, not governance admission; reviewer attribution/separation-of-duties/external distribution would be a separate decision. Authority chain: author creates → governance reviews/registers → L9 mechanically validates/resolves → L7 executes; no step silently transfers ownership.

### D-L9-2 — Procedure: a composition concept, never a second runtime entity (LOCKED 2026-09-08, Q-L9-2)
A Procedure is the reusable method-of-work composed of one pinned workflow definition (deterministic governing skeleton, executed by δ) and one pinned procedure artifact (advisory technique, zero authority). A Skill is the atomic registration/review/versioning/instantiation unit packaging that Procedure with its resource envelope (context contract, grant template, spec template, input schema). Procedure identity = the identity of its pinned workflow + procedure-artifact composition; it is not independently registered, executable, or mutable — standalone Procedure registration would recreate the second-runtime lifecycle just eliminated (D-L9-0). Reuse: Procedure artifacts are immutable/versioned; Skills independently pin their identities — a later procedure@P2 modifies no existing Skill; a new Skill revision must explicitly choose P2. The authority split is total: the control half governs only sequence; the advisory half only suggests (prose inert at δ, proven in L7). Deferred to later questions, not assumed: phase binding of procedure sections (validation semantics), executable-logic boundary (Q-L9-4).

### D-L9-1 — A Skill is a governed, hash-pinned atomic composition (LOCKED 2026-09-08, Q-L9-1)
A Skill is a governed manifest pinning by SHA-256 one complete set of the artifact kinds L1–L7 already execute — workflow definition, workflow ceiling, context contract, grant template, spec template — plus a typed input schema and a **pinned procedure artifact reference** (not embedded: L1 owns instruction identity; embedding would mint a second instruction-identity mechanism inside L9), under a name and version. It is inert data, not an execution engine. **Atomic composition invariant:** the pinned artifacts are resolved as one governed set and cannot be independently mixed or substituted during instantiation (skill A's workflow with grant B is structurally impossible); the composition hash is the identity of the reviewed combination and lands in the L6 record. **Registry NOT pinned:** the capability vocabulary and authorization contracts stay L4-owned; a Skill references required capabilities through its grant template (skill grant ⊆ workflow ceiling ⊆ L4 registry, with L7 phase narrowing at execution) but cannot define or authorize capabilities. If capability-contract pinning is ever needed for reproducibility, that is a specific L4 contract identity, never L9 ownership of the registry. Skill = composition, not capability.

## 3. Grill record (2026-09-08) — all questions CLOSED

**Boundary (locked):** L9 defines, resolves, and validates governed Skills and Procedures in a pre-submission plane; instantiation produces an ordinary governed envelope; L7 alone executes (→ D-L9-0). **Starting principle (owner, locked):** a Skill/Procedure may describe or perform a governed method of work, but it cannot grant authority, create security truth, alter workflow semantics, or bypass the deterministic controls of L1–L7.

### Fold-completeness audit (2026-09-08)
All 17 closures map to D-L9-0..17; no orphaned locks found. Two architecture-doc skill-structure fields were never separately grilled and are dispositioned here: **Failure conditions** — covered structurally, no separate lock needed: failure conditions ARE workflow edges over the closed L7 event taxonomy (@fail targets, exhaustion edges); no skill-level failure vocabulary exists or can exist (D-L9-4/6). **Expected outputs** — NOT designed in this grill: v1 outputs are egress artifacts + advisory content with no skill-declared output contract; flagged to owner at Gate 0 — a declared output contract, if wanted, is a future addition (likely alongside the L10 verification work), not a silent v1 feature.
